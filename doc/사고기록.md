# 사고 기록

내가 이 저장소에서 낸 사고와 그 원인을 적어 둔다. **작업을 시작하기 전에 읽는다.**

감상을 적는 곳이 아니다. 같은 실수를 다시 하지 않으려면 무엇을 확인해야 하는지
적는 곳이다. 그래서 사고마다 **무슨 일이 있었나 → 왜 그랬나 → 무엇을 했어야 했나**
순으로 쓰고, 반복된 것은 아래 '되풀이한 패턴' 에 횟수로 모아 둔다.

새 사고가 생기면 여기에 덧붙인다. 지우지 않는다.

---

## 되풀이한 패턴

같은 뿌리에서 여러 번 났다. 이것부터 본다.

| # | 패턴 | 횟수 | 무엇을 잃었나 |
|---|---|---|---|
| P1 | **앞 명령이 실패했는데 뒤 명령이 그대로 실행됐다** | 3 | `.env` 3개 파괴, `develop` 강제 리셋, 브랜치 규칙 위반 |
| P2 | **화면이 뜨는 것만 보고 "검증했다" 고 보고했다** | 4+ | 흰 화면 배포, 죽은 버튼을 이틀 넘게 방치 |
| P3 | **되돌릴 수 없는 것을 먼저 백업하지 않았다** | 2 | `.env` 복구에 몇 시간 |
| P4 | **확인하지 않고 단정했다** | 4+ | 잘못된 진단을 사용자에게 여러 번 보고 |
| P5 | **남의 작업/내 작업을 확인 없이 덮어썼다** | 2 | 방금 만든 문서 유실, 커밋 재작성 |

## P1 — 실패한 명령 뒤가 계속 실행됐다

### 1. `.env` 3개를 파괴했다 (가장 큰 사고)

**무슨 일** `git worktree add` 가 실패했고, 이어지는 `cd` 도 실패했다. 그런데 같은
줄에 이어 붙인 `ln -sfn A A` 는 그대로 실행되어 **자기 자신을 가리키는 심볼릭 링크**
가 만들어졌다. `.env`, `.env.dev`, `.env.ops` 세 파일의 내용이 사라졌다.

**왜** 명령을 `;` 와 줄바꿈으로 이었다. 앞이 실패해도 뒤가 실행된다.
그리고 되돌릴 수 없는 파일을 건드리면서 사본을 만들어 두지 않았다.

**복구** 운영 API 프로세스가 살아 있어서 `ps eww` 로 환경변수를 읽어 `.env` 를
되살렸다. `.env.dev` 는 되살리지 못해 새로 만들었고 `JWT_SECRET` 이 바뀌어
**개발 서버의 모든 로그인이 무효화됐다.** `.env.ops` 도 새로 만들었다.

**했어야 할 것**
- 명령은 `&&` 로 잇는다. 스크립트는 `set -euo pipefail` 로 연다.
- 되돌릴 수 없는 파일(`.env`, 키, 인증서)은 **건드리기 전에** 사본을 뜬다.
- `ln -sfn` 처럼 조용히 덮어쓰는 명령은 대상 경로를 먼저 출력해 확인한다.

### 2. `develop` 에 `git reset --hard` 를 쳤다

**무슨 일** `git checkout main` 이 실패했는데(운영 워크트리가 이미 체크아웃 중)
이어서 `git reset --hard v2/main` 이 `develop` 위에서 실행됐다.

**왜** P1 과 같다. 그리고 `reset --hard` 를 브랜치 확인 없이 썼다.

**복구** 전부 푸시돼 있어서 `git reset --hard v2/develop` 로 되돌렸다. 운이 좋았다.

**했어야 할 것** `reset --hard` 앞에는 항상 `git branch --show-current` 의 **출력을
직접 보고** 나서 친다. 체크아웃 실패는 곧바로 멈출 이유다.

### 3. 백엔드 커밋이 `develop` 에 직접 들어갔다

**무슨 일** `git checkout ehyun` 이 `package.json` 로컬 변경 때문에 실패했는데,
이어지는 `git add`·`git commit` 이 `develop` 위에서 실행됐다. 브랜치 규칙
(`백엔드는 ehyun`)을 어겼다.

**왜** P1. 게다가 `git push v2 ehyun` 은 **로컬 `ehyun` 참조를 밀기 때문에** 아무
일도 안 하고 성공한 것처럼 보였다. 성공 메시지를 믿고 넘어갔다.

**복구** 해당 커밋의 파일만 `ehyun` 에 다시 올리고 `develop` 을 되감아 머지했다.

**했어야 할 것**
- 커밋 직전에 `git branch --show-current` 출력을 확인한다.
- 푸시 후에는 `git rev-parse v2/<브랜치>` 로 원격이 실제로 움직였는지 본다.

## P2 — "검증했다" 고 했지만 눈으로만 봤다

### 4. 배송이력관리 페이지가 흰 화면으로 배포됐다

**무슨 일** 페이지를 열면 아무것도 안 나왔다. 강력 새로고침도 소용없었다.
사용자가 발견했다.

**왜** `createEmptyDay(date)` 를 `farms` 없이 부른 자리가 있어 빈 `cells` 가
만들어졌고, `farmDayTotal(cells[ch].count)` 에서 터졌다. **브라우저로 한 번도
열어보지 않고 머지했다.**

**고침** 호출부를 고치고 방어적으로 읽게 했다(`93e1f5c`). 이 일 뒤에 Playwright 를
붙였다.

### 5. 보내는 분 주소가 이틀 넘게 저장되지 않았다

**무슨 일** 주문서의 '현재 위치'·'주소 검색' 버튼에 **아무 동작도 붙어 있지 않았다.**
손님이 보내는 분 주소를 넣을 방법 자체가 없었다. 운영 주문 3건에 주소가 비어 있다.

**왜** 그 UI 는 다른 사람이 넣었지만(2026-08-24 `fb53910`), 나는 그 사이 주문서를
여러 번 고쳤다 — 배송 예상일정, 마감 문구, 배송 희망일정. 매번 **화면이 뜨는지와
내가 바꾼 줄이 보이는지만** 봤고 **버튼을 눌러본 적이 없다.** 눌렀으면 즉시 드러났다.

또 하나: `create-order` 는 늘 API 로만 호출해 확인했다. **화면의 입력이 그 API 까지
값을 실어 보내는지는 검증한 적이 없다.** 이번 사고가 정확히 그 틈이다.

**했어야 할 것**
- 화면을 고쳤으면 **그 화면의 버튼을 눌러서** 통과시킨다. 렌더링 확인은 검증이 아니다.
- 주문서를 건드렸으면 **장바구니 → 입력 → 주문 완료까지 실제로 끝낸다.**
- 그리고 **DB 에 무엇이 들어갔는지** 확인한다. 화면에 보이는 것과 저장된 것은 다르다.

### 6. "검증했다" 는 보고 자체가 부정확했다

사용자가 두 번 지적했다 — *"검증은 하고 올렸냐"*, *"실제 브라우저에서 확인하는건
당연한거야."* 맞는 지적이다. 확인한 범위를 넘겨 말하지 않는다. 화면만 봤으면
"화면만 봤다" 고 적는다.

## P3 — 되돌릴 수 없는 것을 먼저 백업하지 않았다

`.env` 사고(1번)가 대표다. 그 뒤로 DB 를 건드리는 작업마다 `server/db/snapshot.sh`
로 이름 붙인 스냅샷을 뜨게 만들었고, 지금까지 24개가 쌓였다. `.env` 3개도 매일
04:30 백업에 포함시켰다.

**규칙** DB 스키마·데이터, `.env`, 키 — 건드리기 전에 스냅샷. 예외 없다.

## P4 — 확인하지 않고 단정했다

### 7. 마이그레이션이 `bankda` 를 체크 제약에서 빼먹었다

`deposit_callback_provider` 를 손보면서 허용 목록에서 `'bankda'` 를 떨어뜨렸다.
그대로 운영에 갔으면 **자동 입금 대사가 전부 멈췄다.** 기존 6행이 제약을 위반하는
것을 롤백 테스트에서 잡아 되살렸다(`3e519d8`).

**규칙** 체크 제약을 바꾸면 **기존 행이 그 제약을 통과하는지** 먼저 센다.

### 8. 같은 오진을 여러 번 보고했다

"저장은 되는데 새로고침하면 0 이 된다" 고 여러 번 말했다. 실제로는 **내 테스트
스크립트가 매 실행 전에 그 행을 지우고 있었다.** 한 번은 편집할 수 없는 `—` 칸을
재고 있었다.

**규칙** 증상을 말하기 전에 **로그와 DB 로 한 번 더** 확인한다. 재현 스크립트가
스스로 상태를 바꾸고 있지 않은지 본다.

### 9. 컬럼을 테이블로 조회해 "운영에 마이그레이션이 빠졌다" 고 할 뻔했다

`to_regclass('public.shipping_fees')` 로 확인했는데 `shipping_fees` 는 **테이블이
아니라 `products` 의 컬럼**이다. 없는 것으로 보여 하마터면 운영에 잘못된 조치를
할 뻔했다.

**왜 이런 확인을 손으로 하고 있었나** 운영 DB 에 마이그레이션 추적 테이블
(`supabase_migrations.schema_migrations`)이 없다. 무엇이 적용됐는지 매번 컬럼
존재로 짐작한다. **아직 고치지 않은 문제다.**

### 10. 자잘한 것들

- 공휴일 API 403 — 포털 키가 이미 URL 인코딩돼 있는데 `httpx` 가 `%` 를 한 번 더
  인코딩했다. `unquote()` 로 풀었다.
- jsonb 배열 저장 실패 — 드라이버가 JS 배열을 PG 배열 리터럴로 보냈다. 사용자가
  *"invalid input syntax for json"* 으로 발견했다. json/jsonb 컬럼 목록을 캐시에
  담아 문자열로 만들어 보내게 고쳤다.
- `date` 컬럼 — 드라이버마다 원하는 타입이 달라 `'YYYY-MM-DD'` 문자열로 통일했다.
- `$COPIED개` — 한글이 변수명에 붙어 빈 값이 됐다. `${COPIED}개`.
- `__pycache__` 19개를 커밋했다. `.gitignore` 패턴이 한 경로만 잡고 있었다.

## P5 — 확인 없이 덮어썼다

### 11. 방금 만든 문서를 `git checkout` 으로 날렸다

문서에 코드 링크를 붙인 뒤 `git checkout develop -- doc` 을 실행했다. 커밋되지
않은 그 수정이 **develop 의 옛 버전으로 덮여 사라졌다.** 스크립트로 만든 것이라
다시 돌려 복구했지만, 손으로 쓴 것이었으면 그대로 잃었다.

**규칙** `git checkout <ref> -- <경로>` 는 **작업 내용을 지우는 명령**이다.
`git status` 로 그 경로에 커밋 안 된 변경이 있는지 먼저 본다.

### 12. 커밋 14개를 다시 써야 했다

`user.name` 이 비어 있을 때 맥 계정명 `lkim` 을 임의로 넣어 커밋했다. 설정이
비어 있으면 채우지 말고 물어봤어야 했다.

## 작업 전 점검표

작업을 시작하기 전에 이 목록을 지나간다.

**시작할 때**
- [ ] 되돌릴 수 없는 것(`.env`, DB, 키)을 건드리나? → 먼저 백업/스냅샷
- [ ] 지금 브랜치가 맞나? `git branch --show-current` 출력을 눈으로 확인
- [ ] 운영에 영향이 가나? → 승인부터 받는다

**명령을 칠 때**
- [ ] `set -euo pipefail`, 명령은 `&&` 로 연결
- [ ] `reset --hard`, `checkout -- <경로>`, `ln -sfn`, `delete` — 대상 먼저 출력
- [ ] 실패 메시지가 보이면 **거기서 멈춘다.** 뒤 명령이 성공한 것처럼 보여도 믿지 않는다

**검증할 때**
- [ ] 화면을 고쳤으면 **눌러서** 확인했나? 렌더링만 본 것은 검증이 아니다
- [ ] 주문서를 건드렸으면 **주문을 끝까지** 넣어 봤나?
- [ ] **DB 에 무엇이 들어갔는지** 확인했나?
- [ ] 검증에 쓴 데이터를 되돌렸나?

**보고할 때**
- [ ] 확인한 범위만 말한다. 못 한 것은 못 했다고 적는다
- [ ] 단정하기 전에 쿼리/로그로 한 번 더 확인한다

## 아직 남은 위험

- 운영 DB 에 **마이그레이션 추적 테이블이 없다.** 적용 여부를 매번 짐작한다.
- 백업 사본이 **이 맥 한 대에만** 있다. 디스크가 죽으면 원본과 백업이 함께 사라진다.
- 노출된 비밀(Gmail 앱 비밀번호, Naver Client Secret)을 아직 교체하지 않았다.
